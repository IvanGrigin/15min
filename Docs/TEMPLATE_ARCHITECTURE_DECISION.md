# Целевая архитектура шаблона 15-минутки

Статус: вертикальный срез реализован и работает (25.07.2026). Разделы 1–9 — обоснование
решения, раздел 10 — что уже сделано и как этим пользоваться.

Цель: один декларативный формат шаблона, который даёт **сразу корректный русский текст**
(падежи, род глагола, согласование при числах, предметы из «своей» вселенной),
**сам считает ответ** из сгенерированных чисел и **не требует нейросети** в рантайме.
Критерий успеха: добавление новой задачи стоит одну JSON-запись и ноль строк Python.

---

## 1. Что реально есть в репозитории (проверено)

Парадигм не четыре, а пять — пятая существует только как контракт в `data/schemas/`.

| # | Что | Где | Текст задачи | Морфология | Ответ | Цена нового шаблона |
|---|-----|-----|--------------|-----------|-------|---------------------|
| A | Модульные генераторы | `problemgen/generation/*_templates.py` (33 файла, ~7200 строк) | f-строки в Python | нет (кроме `count_with_word_ru`) | Python-функция | функция + запись в JSON + правка `source_accounting` + тест |
| B | Архив `all_tasks` | `data/templates/All_tasks_templates.json` (1088 шт.) | текст с `{number_N}` | нет; слотов под слова не существует (только `integer` 3744 и `time` 214) | восстановленная формула или нет | новый PDF-корпус |
| C | Template Studio | `problemgen/template_studio/` (827 строк) | `str.format` | **нет** | `answer_expression` через безопасный AST | одна JSON-запись через админку |
| D | Русский движок | `problemgen/russian/` (324 строки) | слоты `{key:gen_pl}`, `{key:count,n}` | **есть, честная** | нет | — |
| E | Blueprint-контракт | `data/schemas/task_template.example.json` | `text_pattern` — список типизированных узлов | предусмотрена (`case`, `verb_frame`, `number_with_entity`) | `solution_constraints.formula` | не реализовано вообще |

Ключевой факт: **A и B принципиально не чинятся точечно.** В A падеж «зашит» в каждую
f-строку, компилятор ничего не проверит, и следующий разработчик сломает согласование
снова. В B текст неприкосновенен, меняются только числа — отсюда «5 яблока».

## 2. Решение

**Каркас — C. Рендерер — D. Модель данных — E.**

Обоснование по трём слоям:

- **C** уже содержит всё дорогое: декларативное хранение (`data/template_studio/`),
  жизненный цикл `draft → analyze → preview → validate → activate → archive`,
  админку `/admin/template-studio` с CSRF, безопасный вычислитель формул без `eval`
  (`safe_expressions.py`), автопроверку на 10 сидах с **независимым пересчётом ответа**
  (`service.py:_validate_examples`), и уже подмешивается в сборку листа
  (`worksheet_site.py:302`). Поле `grammar_metadata` в схеме черновика зарезервировано —
  автор C планировал ровно эту доработку.
- **D** — единственное место, где морфология сделана правильно: 12 форм задаются явно,
  без автосклонения, поэтому «год → лет» и «человек → людей» работают. Пополнение —
  через JSON, без правки Python (`data/language/nouns/russian_nouns.json`, 100 слов).
- **E** задаёт форму данных, на которую уже ориентируются другие разработчики
  (`entity.example.json` — сущность с 6 падежами; `verb_lexeme.example.json` — глагол
  с формами по роду). Модель данных берём оттуда, **но не берём `text_pattern`**:
  список из 20 узлов на одну фразу невозможно писать руками. Авторская поверхность —
  компактные слоты D; `text_pattern` при необходимости генерируется из них машинно.

## 3. Три дыры, без закрытия которых «сразу без доработок» не получится

Это то, что не видно из README и что надо заложить в план сразу.

### 3.1 `constraints` не исполняется (тихая потеря данных)

Поле `constraints` есть в `EDITABLE_FIELDS` (`service.py:30`) и заполняется анализатором,
но:

- `runtime.py` не упоминает его ни разу (`grep constraints runtime.py` → 0);
- `_active_payload` (`service.py:355`) копирует 11 полей, `constraints` среди них **нет** —
  при активации ограничения просто исчезают.

Значит сейчас нельзя выразить «цена кратна 5», «сдача положительна», «ответ целый».
Нужен цикл rejection sampling: пересэмплировать до N раз, пока все предикаты не истинны,
иначе — ошибка шаблона на валидации, а не кривая задача у ученика.

### 3.2 В вычислителе нет сравнений

`safe_expressions._validate_tree` разрешает только арифметические узлы:
`Compare`, `BoolOp`, `IfExp` отсутствуют в белом списке. Следствия:

- предикаты ограничений из 3.1 писать не на чем;
- нет условных ответов (`a if a > b else b` — типовая формулировка «сколько осталось»);
- сравнения приходится обходить через `min/max`, что покрывает не всё.

Правка маленькая (добавить три типа узлов + операторы сравнения), но обязательная.

### 3.3 Персонажи не имеют падежей и не связаны с предметами

- Единственный боевой реестр — markdown: `Docs/approved_dimensions_150_characters.md`,
  25 вселенных × 6 персонажей, парсится регуляркой в
  `comparison_templates.py:179`. Модель — `Character(universe, name, gender)`, три поля.
- Ни одной падежной формы персонажа в проекте нет. `data/entities/characters/` содержит
  только README и `.example.json`.
- Род определяется эвристикой `_gender_for_name` (`comparison_templates.py:193`):
  окончание -а/-я → женский. На 150 именах даёт ≥15 ошибок (Чебурашка, Незнайка, Кузя,
  Йода, Чубакка, Симба, Муфаса, Пумба, Тотошка, Страшила, Иа-Иа, галчонок Хватайка…).
- Составные имена не склоняются как целое: «кот Матроскин» → «кота Матроскина»,
  «Базз Лайтер» → «Базза Лайтера» — нужны формы обеих частей.
- Предметы (`russian_nouns.json`) с вселенными никак не связаны: в задаче про
  Простоквашино может оказаться световой меч. Требование «предметы в соответствии
  со вселенной» сейчас не выражается вообще ничем.
- Второй, мёртвый реестр — `problemgen/core/story_worlds.py` (19 миров, другие списки
  персонажей), используется только легаси-стеком `domains/` и CLI. Ловушка для нового
  разработчика: два источника правды.

## 4. Целевой формат шаблона

Одна JSON-запись = один тип задачи. Ниже — полная спецификация.

### 4.1 Слоты в тексте

| Слот | Результат | Данные |
|------|-----------|--------|
| `{n}` | число как есть | параметр |
| `{hero}` | имя в именительном | персонаж |
| `{hero:gen}` `{hero:dat}` `{hero:acc}` `{hero:ins}` `{hero:pre}` | падеж, обе части составного имени | реестр персонажей |
| `{apple:count,n}` | «5 яблок», «2 яблока», «21 яблоко» | `russian_nouns.json` |
| `{apple:agree,n}` | «яблок» без числа | то же |
| `{apple:gen_pl}` и др. 12 форм | форма существительного | то же |
| `{hero:g,купил\|купила}` | форма по роду персонажа | **никаких данных не нужно** |
| `{hero:past,купить}` | «купил/купила» из словаря глаголов | `data/language/verbs/` (опционально, позже) |

Про `{hero:g,м\|ж}` отдельно: это дешёвый примитив, который закрывает 90 % проблем
с родом глагола **без создания словаря глаголов**. Автор шаблона пишет обе формы прямо
в тексте; валидатор проверяет, что вариантов ровно два. Словарь глаголов (E,
`verb_lexeme.example.json`) можно добавить потом, не ломая существующие шаблоны.

### 4.2 Пример записи целиком

```json
{
  "template_id": "money_change_01",
  "module_id": "money_purchases_prices_and_calculations",
  "language": "ru",
  "text": "{hero:nom} {hero:g,купил|купила} {item:count,qty} по {price:count,rub} за штуку и {hero:g,дал|дала} продавцу {payment:count,rub}. Сколько рублей сдачи {hero:g,должен|должна} получить {hero:nom}?",
  "parameter_schema": {
    "hero":  { "type": "character", "universe_binds": "story" },
    "item":  { "type": "noun", "tags": ["food", "object"], "universe_binds": "story" },
    "qty":   { "type": "integer", "min": 2, "max": 9 },
    "price": { "type": "integer", "min": 10, "max": 90 }
  },
  "derived_values": {
    "total":   "qty * price",
    "payment": "((total // 50) + 1) * 50"
  },
  "constraints": ["payment > total", "total % 1 == 0"],
  "answer_expression": "payment - total",
  "answer_type": "integer",
  "answer_rendering": { "unit_noun": "рубль", "form": "count" },
  "source_metadata": { "problem_number": "417", "filename": "Docs/20_dengi....md" }
}
```

Что здесь важно:

- `universe_binds: "story"` — и персонаж, и предмет берутся из одной вселенной.
  Это единственный способ выполнить требование «правильные предметы у правильных
  персонажей» декларативно. Реализуется одним проходом: сначала выбирается вселенная,
  потом из неё — персонажи и разрешённые ей предметы.
- `constraints` — предикаты, по которым идёт пересэмплирование (дыра 3.1).
- `answer_rendering.unit_noun` — ответ тоже согласуется: «3 рубля», а не «3 рубль».
- Никакого Python. Никакой нейросети в рантайме: LLM участвует только на этапе
  `analyze` в админке (черновик из старого текста), и её результат обязан пройти
  валидацию на 10 сидах.

### 4.3 Конвейер генерации экземпляра

```
seed
  ↓
выбор вселенной (если есть слоты с universe_binds)
  ↓
sample_parameters      integer/decimal/choice → числа
                       character → объект с падежной парадигмой
                       noun      → RussianNoun из словаря, отфильтрованный по вселенной и тегам
  ↓
derive_values          безопасный AST, топологический порядок (уже есть)
  ↓
constraints            все предикаты истинны? нет → пересэмплировать (до 200 попыток)   ← новое
  ↓
answer_expression      → answer                                                        (есть)
  ↓
render                 слоты D вместо str.format                                       ← новое
  ↓
answer_rendering       «12 рублей»                                                     ← новое
```

Детерминированность: `(template_id, seed)` → всегда один и тот же экземпляр, включая
выбор вселенной и персонажей. Это уже обеспечено передачей `random.Random(seed)`.

## 7. Порядок работ

1. **Вертикальный срез** (1 шаблон end-to-end): правки 1–7 + 10 персонажей одной
   вселенной + один реальный шаблон `money_change_01`, проходящий валидацию на 10 сидах.
   Это доказывает схему до массового заполнения данных.
2. **Реестр 150 персонажей** с падежами. Чисто данные, распараллеливается,
   проверяется скриптом-валидатором (все 6 форм непусты, род задан, имя совпадает
   с markdown-таблицей).
3. **Перенос модулей с подтверждёнными дефектами** — по одному:
   `motion_002_pursuit`, `money_003_change`, `work_*`, `process_*`, `calendar_*`,
   `clock_*`. После переноса модуль выключается в A.
4. **Привязка предметов к вселенным** и добор лексики.
5. Остальное — по мере поступления новых задач: новые пишутся сразу в новом формате.

## 8. Риски и что мешает

- **Тест цементирует обходной путь.** `tests/test_russian_variable_agreement.py:66`
  требует `assertIn("Персонаж", problem.problem_text)` — то есть канцелярской формулировки
  «Персонажи: Эльза и Крош», которой в `age_templates.py` избегают склонения.
  При переходе на нормальные падежи тест переписывается.
- **Два реестра персонажей** (`story_worlds.py` vs markdown) — свести к одному
  до того, как другие разработчики начнут использовать оба.
- **Валидация покрытия номеров в A**: `load_*_templates()` падает, если
  `source_problem_numbers` не совпадают с разбором `Docs/*.md`. При выключении шаблона
  в A нужно синхронно править `source_accounting.json`, иначе упадёт загрузка всего модуля.
- **Решение стоит принять до** того, как в A добавят ещё десяток модулей: каждый новый
  модуль в A — это +200–600 строк f-строк, которые потом придётся переносить руками.

## 10. Вертикальный срез: что уже работает

Реализовано и покрыто тестами (`python3 -m unittest discover -s tests` — 291 тест, OK).

### 10.1 Новые возможности

- **Падежи и род из данных.** `data/entities/characters/approved_characters.json` —
  18 персонажей трёх вселенных с шестью формами полного имени
  («кота Матроскина»), явным родом, флагами `indeclinable` и `lowercase_start`.
  Загрузчик — `problemgen/russian/characters.py`. Эвристика `_gender_for_name`
  в новом пути не участвует: тест фиксирует, что «галчонок Хватайка» — мужского рода.
- **Слоты вместо `str.format`.** `{hero:gen}`, `{metre:count,tail_m}`,
  `{hero:g,шёл|шла}`. Рендерит `problemgen/russian/template_engine.py`,
  Studio вызывает его из `runtime.render_template`. Заглавная буква ставится
  в начале каждого предложения — имена со строчной буквы работают корректно.
- **Дробные количества.** «2,5 часа», «11,5 километра» — дробь управляет
  родительным падежом ед. ч., число печатается с запятой.
- **`constraints` исполняются.** Rejection sampling до 300 попыток;
  предикаты пишутся обычными сравнениями, для чего в `safe_expressions`
  добавлены `Compare`, `BoolOp`, `IfExp`. `constraints` теперь копируются
  в активный шаблон (раньше терялись при активации).
- **Отчёт о подборе.** Валидация показывает долю удачных попыток
  («попыток подбора 161, отсеяно constraints 151, доля удачных 6%») и падает,
  если при подборе была ошибка вычисления — иначе пересэмплирование
  молча прятало бы деление на ноль.
- **Ответ с единицами.** `answer_rendering.parts` → «1) 11,5 километра; 2) 10 минут».
- **Приоритет Studio на сайте.** `worksheet_site.py`: если у модуля есть активные
  Studio-шаблоны, старый генератор для него не вызывается (было: 1 шанс из 12).

### 10.2 Два шаблона про путь по частям

`scripts/seed_worksheet_templates.py` — заводит их через полный цикл
draft → validate → activate. Python-кода на задачу: ноль, всё в JSON-структуре.

```bash
python3 scripts/seed_worksheet_templates.py --preview   # посмотреть примеры
python3 scripts/seed_worksheet_templates.py             # завести/переактивировать
```

**Базовый** (`motion_half_path_half_time_ride`) — исходная задача про хоббита:
половина пути со скоростью `v1`, половина всего времени со скоростью `v2`,
остаток верхом. Спрашивается путь пешком и время верхом.

**Повышенный** (`motion_third_path_third_time_ride`) — треть пути, треть времени,
остаток верхом с известной скоростью. Два неизвестных, обратный ход рассуждения.

### 10.3 Разбор математики (важно для новых шаблонов этого типа)

Пусть доля первого участка пути — α, доля всего времени на втором участке — β,
хвост — `c`, полное время — `T`.

```
S(1-α) = v2·βT + c        →  S = (v2·βT + c) / (1-α)
t1 = αS/v1 ,  t2 = βT ,  t3 = T - t1 - t2 > 0
```

Из условия `t3 > 0` при **α = 1/2** следует `v2 < v1 - 2c/T`: второй участок
структурно **всегда медленнее** первого. Поэтому «шёл 6 км/ч, бежал 5 км/ч»
в исходной задаче — не опечатка, а неизбежность, и текст шаблона описывает
второй участок как «устал и пошёл медленнее». Бег быстрее ходьбы возможен
только при меньшей доле пути: при **α = 1/3** допустимо `v2 < 2v1` — это и есть
повышенный уровень.

Второе следствие: в исходной задаче лошадь везёт последние 500 м за 10 минут,
то есть со скоростью 3 км/ч — медленнее пешехода. Ограничение `ride_kmh > v1`
не даёт генератору выпускать такие условия (исходный набор чисел при этом
отсекается — это осознанное улучшение задачи, а не её воспроизведение).

Слепой перебор по такой схеме даёт доли процента годных наборов, поэтому шаблоны
параметризованы «обратно»: свободны скорость, разрыв скоростей, время верхом и
хвост, а время бега выводится из тождества

```
run_min · delta = 3·tail_m/50 + v1·ride_min
```

Доля годных наборов — около 6 %, медиана 15 попыток при лимите 300.
